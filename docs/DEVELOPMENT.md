# 行程规划器

地图上标注想去的地方，自动按天分组、排游览顺序，并给出每一段的地铁/公交乘车方案（上车站、下车站、线路、换乘、耗时）与步行衔接。

纯本地运行，不依赖任何云端服务；只有一个外部依赖——腾讯位置服务的 WebService Key（可选，见下文「关于 Key」）。

---

## 界面

打开先看到**首页**：

- 顶栏三段导航：我的旅行 / 足迹 / 收藏
- 中间是最近一次旅行的大卡片（城市名、旅客数、日期区间、地点数）；没有地点时显示「新行程」空态
- 下面四张统计卡：已去过城市、旅行总数、旅行天数、累计里程
- 右下角「＋ 新建行程」：**把当前这段存起来**，再开一张空白行程直接进规划器
- 卡片下方是「全部行程」：所有存过的行程都在，点一下切换回去，× 删除。当前这段不出现在列表里
  （它正在编辑），切换时会把当前这段自动存回去，所以来回切换不会丢数据
- 点「开始规划」进入原来的规划器；「足迹」是一个中国地图，把去过的城市打成气泡
- 地点标记默认**固定不可拖**（拖动容易误改坐标）；要改位置用详情里的「在地图上重定位」，
  或在地点卡片点 ☆ 收藏、在详情里填「图片链接」让圆圈显示照片（不填则用分类色块）

中国地图用的是高德底图 + 城市点位，**不自己画省级边界**——国界、台湾、南海诸岛必须符合国标，
自制的省界 GeoJSON 很容易画错，属于合规红线。

## 两种用法

### A. 单文件版：`travel-planner.html`（双击即用）

所有代码、样式、Leaflet 都打进了一个 HTML，**内置了 Key**。
双击用浏览器打开就能用，不用装 Node、不用启动服务、不用命令行。

接口走 JSONP 直连腾讯位置服务：腾讯不返回 CORS 头，但支持 `output=jsonp`，
所以浏览器可以直接调。请求在页面里排队（间隔 280ms）并做限流重试，
和走服务端时一样不会打爆 QPS。

这个文件是用脚本生成的，改了源码要重新生成：

```bash
node build-standalone.js                                  # 不内置 Key
TMAP_KEY=你的Key node build-standalone.js                  # 内置 Key（推荐）
```

**单文件版的取舍**：导图只能走浏览器下载，会被 Windows 打上「网络来源」标记，
XMind 打开时弹一次「文件可能有害」，点确定或解除锁定即可（原因见下文）。

### B. 本地服务版：双击 `start-background.bat`（后台常驻，功能最全）

接口走 Node 代理，有 6 小时缓存和更稳的串行节流；导图直接写本地文件、不弹安全提示；
还能一键打开导出目录。要长期用、或经常导出，用这个。

**后台常驻**

| 文件 | 作用 |
| --- | --- |
| `start-background.bat` | 双击：无窗口跑起服务，然后自动打开浏览器。关掉任何终端都不影响 |
| `stop-background.bat` | 双击：按 `.server.pid` 里的进程号停掉服务 |
| `start.bat` | 前台运行（带控制台，能看到日志，Ctrl+C 停止） |
| `.server.pid` | 服务启动时自动写、退出时自动删，别手动改 |

想开机自启：`Win+R` 输入 `shell:startup`，把 `start-background.bat` 的**快捷方式**放进去。

**Key 放在 `key.txt`**（同目录，只写一行）。优先级：`--key` 参数 > 环境变量 `TMAP_KEY` > `key.txt`。
换 Key 就改这个文件，不用动脚本。

## 启动

双击 `start.bat`，或在命令行：

```bash
node server.js
```

浏览器自动打开 <http://127.0.0.1:8787/>。

其他参数：

```bash
node server.js --port 8899                 # 换端口
node server.js --key ABCD1-EFGH2-...       # 启动时内置 Key（免去页面填写）
set TMAP_KEY=ABCD1-EFGH2-... && node server.js   # 或用环境变量
node server.js --no-open                   # 不自动开浏览器
```

要求 Node.js 18+（用到了内置 `fetch`）。无第三方 npm 依赖，不用 `npm install`。

## 怎么用

1. **添加地点**，三种方式：
   - **搜名字**：输入「全聚德」「汉庭」「南锣鼓巷」，下拉里会显示识别出的类别、区和完整地址，点一条即添加；
   - **输地址**：只有门牌号也能用，比如「建国路87号」。输入框下方会出现「📍 按地址定位」一行，
     走地址解析精确落点。城市缺省会按设置里的城市自动补；
   - **点地图**：直接在地图点一下，有 Key 时会自动反查地名、类别和所在区。
2. **设置行程**：左侧设置分成三页，一次只看一屏，不用往下翻——
   - **基本**：只剩「每天开始 / 结束时间」。城市由第一个添加的地点自动推断（搜索走全国），
     日期默认今天，天数在「分天」里加减——设置区不再堆一屏表单。
   - **偏好**：出行偏好、节奏、午餐 / 晚餐时间、餐饮安排、每晚回住处、装不下时是否自动舍弃
   - **分天**：加减天数；点某天的「选地点」把地点勾进那一天，然后点右下角**「应用」**——
     这时会进入**严格模式：只排你亲手选进各天的地点**，没选的一个都不排（顶部会写明有几个未选）。
     点「恢复自动补点」退出严格模式，回到「没指定的天按位置自动分配」。
     严格模式下新增的地点默认不参与，记得也给它选一天。
   - **往返**：酒店、到达站 / 返程站及时间（**没填全时这个页签右上角有个橙点**）
3. **点「规划」**：只有点击才算，改动不会自动重排（按钮上会出现 `规划 •` 提示有改动）。

**营业时间是真约束，不是装饰。** 从高德拿到的 `hours`（如「周一至周日 09:00-17:00」）会被解析成
开门/关门时间参与排程：太早到就等，来不及就换顺序，实在不行在节点上标红。
解析规则：取所有时间段的「最早开门」到「最晚关门」；「全天开放」不约束；跨夜（如 10:00-07:00）当成开到当天结束。
像「11:00-14:30,16:30-21:00」这种中途休息的，只保证在营业区间内，午休时段不额外拦。

**AI 排的是「顺序 + 停留」，本地算的是「时刻」。** 分工是这样的：

| 谁 | 管什么 |
| --- | --- |
| DeepSeek | 哪天去、当天先去哪后去哪、每个点建议待多久、为什么这么排（一句话） |
| 本地排程 | 按顺序和停留，算出每段的到达/离开时间、通勤、饭点、超时判断 |

为什么不让 AI 直接给「09:41 到故宫」：它给不出可执行的分钟表，硬答就是编的。

AI 的判断依据（写进提示词）：闭馆日、热门景点上午人少、夜景放傍晚、大景区给足时间、
同一天别横穿城市、每天最多 2 家正餐、必去优先。地点自带的营业时间也会一起发过去。

输出 `{"days":[{"d":1,"items":[{"id":"p1","stay":180,"why":"上午人少，需三小时"}]}]}`，
写回 `place.day / seq / minutes / aiNote`。**每个点建议的停留会直接用在行程里**，
你也可以在行程节点上直接改那个数字——改过就标记为“用户设定”，之后 AI 不再覆盖。

**关于「检索全网」**：DeepSeek 的对话接口**不联网**，它靠训练知识判断（故宫周一闭馆这类常识没问题，
但新开的店、临时闭园它不知道）。要真联网得另接一个搜索 API（博查 / Serper / Bing 之类），
需要你提供对应的 key。现在的做法是：能拿到的硬数据（营业时间、评分、人均）走**高德**，
判断性的事（什么时候去合适）交给模型。

接口支持 CORS（含 `file://`），单文件版可以直连；Key 在 `ai.js` 顶部，也可以用
`localStorage.setItem('aiKey','...')` 覆盖。设置里「偏好 → 用 AI 优化分天」可以关掉。
4. **看方案**：右栏按天给出时间轴，每个地点之间插入一段出行卡片。
   右栏顶部「行程 / 预算」右边有个**路线开关**——关掉后地图上只留点位不画连线，方便看清每个点落在哪、彼此多远。
   - **坐车**：点卡片展开逐段指引（步行多少米到哪个站口、坐几号线往哪个方向、几站、在哪站下、再走多少米）
   - **纯步行**：只显示「步行 16 分 · 1.1 公里」，不展开逐段拆解——一条路拆成七个「步行 XXX 米」没有任何用处
5. **分地区查看**：左侧地点列表可按「按地区」或「按行程」切换。按地区时按区县分组，
   点多了用上方的**搜索框**就地过滤（名称、地址、区、类别都能匹配），按 Esc 清空。
   每组显示地点数和总停留时长，点组标题折叠/展开。行程每天标题和图例也会标出当天覆盖哪些区。
6. **调整**：
   - 拖地图上的标记 → 修正坐标；
   - 卡片里的「第X天」→ 手动指定某天（之后不再自动分天）；
   - 时间轴上地点标题右侧的 `↑ ↓` → 调当天顺序（会把整套方案冻结，点「自动规划」可解冻重排）；
   - `⏰` → 给地点加「最晚到达时间」（适合预约制博物馆）；
   - `×` → 删除。
7. **导出**：三种，够用就好。**Markdown 和导图末尾都会附一份「全部地点（按类别）」清单**，
   把加过的店按 餐饮 / 景点 / 博物馆 / 购物 / 住宿 / 交通枢纽 分开列，带地址、停留时长、门票、电话——
   相当于一份可以照着走的地址簿：
   - **复制**：整份行程的纯文本，粘到微信/邮件里
   - **MD**：Markdown 文件，含每段乘车明细
   - **导图**：`.xmind` 文件，**双击直接用 XMind 打开**，打开即可编辑。
     用模板的 `timeline.left` 结构和默认彩虹主题，**不带表情符号**，只讲行程本身：

     ```
     北京 3 天
     └─ 第1天 11月20日 东城区/海淀区
        ├─ 08:30 北京南站 出发
        ├─ 09:41-12:41 故宫博物院
        │  ├─ 地址：东城区景山前街4号
        │  └─ 通勤：地铁1号线 → 8号线，18分，¥3
        └─ 12:41 午餐
     ```

     最后还有一个「全部地点（按类别）」分支，当地址簿用。
     **文件会直接写到 `travel-planner/exports/`**，不经过浏览器下载；
     保存后弹出的提示里有完整路径，点提示上的「打开文件夹」直接跳到那个目录

所有改动自动存 localStorage，下次打开还在。

### 行程闭环：从到站到返程，中间不留断头

一个真实的行程是这样串起来的，工具现在就按这个串：

```
出发城市 ──(高铁/飞机，你自己订)──▶ 到达站 ──▶ 酒店放行李 ──▶ 每天景点 ──▶ 每晚回酒店 ──▶ 返程站 ──▶ 出发城市
```

在设置里填这几项就会自动闭环：

| 字段 | 作用 |
| --- | --- |
| 出发城市 | 只做展示和返程提示 |
| 到达城市 | 搜索用的城市范围 |
| 大人 / 小孩 | 预算按「成人全价 + 儿童 6 折」折算 |
| 到达站 + 到达时间 | 第一天从这里开始，先接驳到酒店放行李再出门 |
| 返程站 + 发车时间 | 最后一天提前 30 分钟到站，自动从酒店送站 |

**这三个地方都是直接填名字，不用点地图**——地图上选点很难选准。填「北京南站」「如家酒店(北京王府井店)」
这类真实名称，工具会自动解析成坐标，下方显示 `✓ 全季酒店(北京天安门广场王府井店) · 东城区` 让你核对；
匹配到多个同名地点时会出现下拉让你选；填错了就重新填，或者点「清除」。

解析失败会明确告诉你「没找到」，不会静默用错坐标。地图上会用 `到`／`返` 两个小方块标出这两个站点，
一眼能看出解析对不对。

**每天那个结束时间是「回到酒店」的时刻，不是最后一个景点玩完的时刻。**

时间轴最后一定有一个终点节点：`19:56 回住处 → 20:54 回到酒店`；
最后一天是 `17:57 回酒店 → 18:25 去车站 → 18:58 到站`。
每天标题右侧的收工时间后面标了 `回到酒店` / `到站`，明确它指的是哪一刻。

如果没填酒店，就没有返程段，每天会结束在最后一个景点——这种情况会直接提示你，不会让你自己发现。

**闭环是怎么算进时间的**

- 第一天：`到达时间` 到站 → 真实地铁路线到酒店 → 20 分钟放行李 → 才开始第一个景点。
  所以第一天能塞的点会明显变少，这是对的。
- 每天结束：默认「每晚回到住处」已勾选，最后一段固定是 `最后一个景点 → 酒店`。
- 最后一天：`景点 → 酒店取行李 → 返程站`，且必须不晚于「发车时间 − 30 分钟」。
  排不下会自动舍弃可选地点，被舍弃的会在左侧列表标上「未安排」。

如果没定返程站，可以填「最后一天提前收工 N 分钟」来留出返程余量。

**边界**：工具**不查也不排**城际高铁/航班的班次——那需要时刻表数据源，腾讯位置服务没有。
你只需要把「几点到、几点走、在哪个站」告诉它，中间全部由它排。

### 多套方案对比

顶栏点「方案对比」，会同时算出三套方案：

| 方案 | 区别 |
| --- | --- |
| 均衡 | 按地理分区，默认 3 天 |
| 紧凑 | 压到 N-1 天，每天多排 45 分钟 |
| 轻松 | 放宽到 N+1 天，每天提前 1 小时收工，每天最多 4 个点 |

对比表直接列出覆盖地点数、总在途、步行距离、车费、最长单段、最晚结束时间、是否超时、舍弃几个点，点「采用」替换当前方案。

三套方案用的是**同一套估算模型**，所以比较是公平的；采用后才会去拉真实地铁/公交路线。

### 别人给你加的那三个字段：评分 / 营业时间 / 人均

**腾讯位置服务没有这些字段。** 我查过 `place/v1/search` 和 `suggestion` 的完整返回：
只有名称、地址、分类层级、坐标、区县、电话。没有评分、没有营业时间、没有价格。

所以这个工具**不会编造**它们。详情弹层里那一行写的是「腾讯位置服务无此字段」。
门票价格需要你自己填（填了才计入预算）。要评分数据得换数据源（大众点评/携程没有公开 API）。

### 预算与记账

右栏切到「预算」页：

- **交通**：市内交通用规划结果里每段的**真实票价**累加（走路不计费），
  再加上**往返大交通**——填「往返大交通 ¥/人」，出发城市到到达城市的往返都算进去（含儿童 6 折）
- **门票**：你在详情里填的单价 × 人数
- **住宿 / 餐饮 / 杂费**：按单价推算，单价可以改
- 填了总预算后，进度条实时显示还剩多少 / 超支多少

记账支持一句话：输入「午饭 128」「打车 35」「门票 60」直接识别金额和类别。

### 天气与临时调整

- 每天标题会带天气预报（晴/雨/温度/降雨概率），数据来自 Open-Meteo，不需要 Key，覆盖未来 16 天
- 降雨概率 ≥ 60% 时，当天标题上的天气标签会变蓝提示
- **临时去不了**：点地点名称打开详情 → 「这次不去」，该点立即从行程移除并重排，随时可以恢复
- **延误**：直接改「每天开始时间」，整条行程跟着后移
- 改完点「自动规划」重新分天

### 详情与附近推荐

点地点卡片右侧的 `ⓘ`，或行程里点地点名字，打开详情：

- 地址、地区、分类、**电话**、坐标
- 停留时长、门票单价、最晚到达时间
- 「附近推荐」：按 2 公里范围搜周边餐厅/咖啡/景点/商场/地铁站，
  每条会算**顺路代价**（`+8 分` 意思是插进当天行程只多花 8 分钟），顺手就加进同一天

### 餐厅会被识别，并按饭点排进去

选地点时如果挑的是饭馆，工具会自动识别成「餐饮」，然后**当成那一餐的锚点**：

| 项目 | 规则 |
| --- | --- |
| 识别 | 腾讯分类里带 `美食`（如 `美食:中餐厅:北京菜`）直接判为餐饮；名字兜底覆盖 全聚德 / 海底捞 / 星巴克 / 眉州东坡 等连锁 |
| 午餐锚点 | 默认排进 **11:30–13:30**，晚于 13:30 才算违规 |
| 晚餐锚点 | 卡片上把餐次切成「晚餐」，排进 **17:30–19:30** |
| 替代关系 | 当天有餐厅，就**不再额外插**「午餐」块——不会让你吃两顿 |
| 保留优先级 | 时间不够要舍弃时，餐厅**最后才丢**；先丢景点 |
| 太早也不行 | 早于窗口 1 小时以上（比如 15:20 吃晚饭）算违规，排序会把它往后挪；实在排不进就**跳过不排**，并告诉你哪家没排上 |
| 集中指定 | 设置 → 偏好 → 「餐饮安排」：列出所有已添加的餐厅，逐家选**午餐 / 晚餐 / 小吃**，右侧直接显示被排到第几天几点 |
| 小吃 | 选「小吃」= **不锁饭点**，顺路就买，不占正餐位，也不参与"太早太晚"的偏离计算。切过去时停留会从 75 分钟自动压到 20 分钟 |

排出来的效果（实测）：

```
第2天  天安门 08:49 → 国博 09:57 → 🍜全聚德 11:30–12:45
       → 前门大街 13:32 → 天坛 15:22 → 🍜四季民福 18:14–19:29
```

当天没有餐厅时，才会按设置里的「午餐 / 晚餐时间」补一个通用餐块（晚餐只在给回酒店、
去车站留足时间时才补，不会把你逼到赶不上车）。

### 类别是怎么识别出来的

分两级，先看接口给的分类，再看名字：

1. **接口分类**：腾讯返回的 `category` 是层级串，如 `美食:中餐厅:北京菜`、`酒店宾馆:经济型酒店`、
   `旅游景点:城市广场`。按一级目录直接映射到 景点 / 博物馆 / 餐饮 / 购物 / 住宿 / 交通枢纽。
2. **名称兜底**：很多地方名字里根本没有「酒店」「餐厅」二字，所以补了品牌词表——
   `如家 / 汉庭 / 全季 / 亚朵 / 希尔顿 / 万豪 …` → 住宿；`全聚德 / 海底捞 / 星巴克 / 瑞幸 / 眉州东坡 …` → 餐饮。
   这一步主要给「按地址添加」和手动命名的地点用。

识别结果会带入默认停留时长（景点 120 分、餐饮 75 分、住宿 20 分…），可以随时在卡片里改。

## 规划逻辑

不是随机分配，按这个顺序算：

1. **全局链**：从住处出发做最近邻巡回，再用 2-opt 打磨成一条不折返的路线。
2. **分天**：沿这条链做连续切段（动态规划），目标是最小化在途时间 + 让每天负荷均衡 + 严格不超出每日时长。因为切的是连续段，同一天的地点在地理上必然相邻。
3. **每天内部排序**：最近邻 + 2-opt，起终点是住处。
4. **时间轴推演**：从每天开始时间逐段累加，插入午餐、处理「等景点」和最晚到达约束，算出实际到达/离开时刻。
5. **真实耗时替换**：有 Key 时按最终排好的顺序逐段请求真实公共交通方案，再把真实耗时喂回去重排一次（最多 3 轮），所以展示出来的时间是自洽的。

**可行性校验**不靠一堆弹提示，而是把信息放在它该在的地方：

- **超时** → 直接标在那一天的标题上（`08:30–22:40 超出 1 小时 40 分`），红色
- **装不下被舍弃** → 汇总条给一句「另有 N 个地点因时间不足未安排」，左侧对应卡片打上橙色 `未安排` 标记
- **是估算还是真实路线** → 每段路自己带标签，不用全局提醒
- **天气异常** → 静默忽略，不打扰

跨区过远的提醒、以及「部分路段是估算」这类全局提示已经去掉了——它们一天刷好几条，占了半屏，
真正要动手的时候反而找不到重点。

### 坐标与底图

统一用 **GCJ-02**（腾讯接口返回的坐标系）。底图是高德栅格瓦片，同样是 GCJ-02，所以标注位置是对齐的。换成 OSM 底图会整体偏移几百米，别换。

## 关于 Key

**没有 Key 也能完整跑通**：分天、排序、时间轴、地图、导出都正常，只是每段路程用几何模型估算
（路网绕行 1.28 倍，地铁平均 26 km/h，加进出站与候车约 16 分钟），并明确标为「估算」。
这种情况下**不会**有线路名和站点名——因为那必须走真实接口。

本机的 `start.bat` 里已经写入了你提供的 Key（`TMAP_KEY` 一行），双击即可直接用真实数据。
要换 Key：改 `start.bat` 那一行，或者在页面右上角「数据源」里填（存在浏览器 localStorage）。

自己申请：

1. 打开 <https://lbs.qq.com/dev/console/application/mine>，注册并创建应用；
2. 添加 Key，**勾选「WebServiceAPI」**，IP 白名单留空；
3. 把 Key 粘到页面右上角「数据源」里，点「保存并校验」。

### 配额与限流（实测踩过的坑）

个人 Key 的**每秒请求数上限很低**，并发抓路线会直接返回「此key每秒请求量已达到上限」。
服务端已做两件事：

- 所有上游请求串行排队，最小间隔 260ms（可用 `TMAP_INTERVAL` 环境变量调整）；
- 被限流时指数退避重试 4 次。

一次 12 个地点、3 天的规划大约消耗 25–40 次路线请求，耗时 8–12 秒。
把间隔调到 150ms 以下大概率会被限流，别调。

常见报错对照：

| 现象 | 原因 |
| --- | --- |
| `status 311` / Key 无效 | Key 填错，或没勾 WebServiceAPI |
| `status 120` / 每秒请求量已达上限 | 间隔太短，调大 `TMAP_INTERVAL` |
| 校验通过但路线全失败 | 该 Key 未开通「路线规划」相关服务 |

接口一览（都走本地服务，Key 通过 `X-Tmap-Key` 头传）：

| 接口 | 说明 |
| --- | --- |
| `GET /api/suggest?keyword=&region=` | 输入提示（带类别、区县、adcode） |
| `GET /api/search?keyword=&region=` | 地点搜索 |
| `GET /api/geocode?address=&region=` | 地址解析，缺城市会自动补前缀 |
| `GET /api/reverse?lat=&lng=` | 逆地理（点地图时取名 + 补区县） |
| `GET /api/leg?from=&to=&mode=&policy=` | 单段路线，`mode` = transit / walking / driving |
| `GET /api/weather?lat=&lng=&start=&days=` | 天气预报（Open-Meteo，免 Key） |
| `GET /api/nearby?lat=&lng=&radius=&keyword=` | 周边搜索，带距离 |
| `GET /api/config` | 服务端是否内置了 Key |
| `GET /api/health` | 校验 Key 是否可用 |

`/api/leg` 会把腾讯的原始结构归一化成前端直接可用的 Leg（含 `steps[]`：walk / ride / drive），
并把 `polyline` 解压成坐标数组用于画线。归一化细节在 `server.js` 的 `normalizeTransitRoute()`。

**两个接口层面的坑（都已在代码里处理，改代码时别踩回去）：**

- `place/v1/suggestion` 把 `data` 放在**响应顶层**，不像别的接口包在 `result` 里。
  `checkTencent()` 现在返回 `json.result || json` 兼容两种。
- `geocoder/v1` 的 `address` **必须带城市**，否则直接返回 `348 参数错误`。
  「沙井胡同12号」查不出来，「北京市沙井胡同12号」才行，服务端会自动补前缀。

## 规划时到底调了哪些接口

一次「规划」实测（6 个地点、单城市）：

| 请求 | 次数 | 用途 |
| --- | --- | --- |
| 腾讯路线（transit / walking） | 40 上下 | 每两个相邻地点一段，真实地铁公交方案 |
| DeepSeek | 1 | 决定「哪天去哪几个点」 |
| Open-Meteo 天气 | 1 | 每天头部的天气标签 |

**这些数据真的进了行程**：规划完 6 段路线全部有线路名（`回住处 · 地铁14号线 → 地铁8号线`），不是估算。

**不会重复烧配额**：
- 没有改动就点「规划」→ 直接提示「没有改动」，**不发任何请求**
- 改过东西（比如加了一天）→ 只把按钮标成 `规划 •`，**不会自动规划**，等你点
- 点下去后只请求**缺的那部分路段**（已有缓存复用），AI 会重新参与分天

**AI 什么时候不参与**：你在「分天」里手动指定过某天，就完全按你的来。
AI 自己分的天会打 `dayAuto` 标记，不算手动，所以下次改完再规划它还会重新优化。

## 排程约束（都有测试覆盖）

`node _constraints-test.js` 跑一遍，24 项全过。改规划逻辑前后都该跑。

| 约束 | 生效方式 |
| --- | --- |
| 每天开始 / 结束 | 直接决定当天起止；结束时间还会被「节奏」微调（轻松 −60 分、紧凑 +45 分） |
| 出行偏好 | 真实路线模式下作为 API 的 `policy`（地铁优先 / 少换乘 / 少步行…）；估算模式下只有「仅步行 / 打车」有区别 |
| 节奏 | 只改收工时间 + 轻松模式每天最多 4 个点，**不改停留时长**——偷偷压缩停留是最容易让人踩坑的做法 |
| 午餐 / 晚餐时间 | 通用餐块按设定时刻插入；**餐厅的锚点窗口也跟着这个设置走**（原来写死 11:30–13:30 / 17:30–19:30） |
| 午餐 / 晚餐开关 | 关掉就不插通用餐块 |
| 餐饮安排 | 午餐/晚餐店锁在饭点前后，小吃完全不锁、顺路就买 |
| 最晚到达 | 超过就记违规，**并把它当成可挪动的对象参与重排**；实在排不下会在节点标红「晚于 10:00 到达」，顶部提示条同步汇总 |
| 营业时间 | 早于开门就等（最多 120 分钟），关门前来不及就记违规并重排；实在排不下在节点上标红「超出营业时间」 |
| 停留时间 | 每个点自己的分钟数，直接决定离开时间 |
| 必去 / 想去 / 可选 | 装不下时按优先级舍弃；必去永不丢 |
| 分天锁定 | 指定了哪天就锁在哪天，其余的点按位置补 |
| 到达 / 发车时间 | 第 1 天不早于到达时刻；末日不晚于发车前 30 分钟 |
| 提前收工 | 没填返程站时，按「提前 X 分钟」把当天结束时间往前挪 |
| 自动舍弃 | 开：装不下就丢掉优先级低的；关：宁可超时也不丢 |

**餐饮密度**：同一天最多 2 家正餐（午/晚各一）。超出的会先搬到餐饮少的那天；搬不动且不是必去，就标成未安排。
不给这条约束的话，AI 很容易把一条小吃街整条塞进同一天，结果从早吃到晚。

**排不完就跨天搬**：某天怎么裁都超时（多半个个都是必去），会把末尾的点挪到别的天，
而不是硬排到 23:28。搬不动才会保留超时并在日程头标红。

**导出带资料和攻略**：Markdown 和导图里每个地点都记录地址、营业时间、评分、人均、门票、电话，
再加一条 AI 写的游玩建议（怎么玩、怎么避坑，25–60 字）。
第一次导出会等几秒（AI 正在写），写完存进 `place.tips`，以后再导出直接复用。

**舍弃策略**：先按优先级（必去 > 想去 > 可选），同级再按「停留越长的越先丢」——
因为丢一个长点能最快把时间省回来。所以全部标成「想去」时，故宫（120 分）会先于景山（60 分）被丢。
想保住某个点，标成**必去**。

**裁剪后会回填**：只裁剪不补，常常丢过头（曾出现为了 7 分钟超时丢掉 75 分钟的点，当天 11:46 就收工）。
现在裁剪完会把丢掉的点按「必去优先、停留短的优先」再塞回去，塞得进就收回。

## 跨城行程不做日程

地点分属两个及以上城市时，导图**不排逐日时间轴**，只按城市整理地点清单，
根节点写明「跨城不做日程安排」。理由很简单：城际交通（高铁/航班）没有数据源，
硬排出来的时间全是假的，不如老实说不排。

单城市行程正常输出逐日时间轴。

## AI 规划（热门路线参考）

右栏「行程方案」标题栏，「导图」后面有个 **AI规划** 按钮。点它拿当前城市和天数去问 DeepSeek，
返回 3 条热门经典路线，以**可审阅的方案**展示，**不覆盖你现有的规划**：

```
北京中轴线经典三日          3 天 · 8 个地点        [加到我的规划]
第一次来北京适合这条，中轴线一网打尽
D1 天安门广场 故宫博物院 景山公园
D2 天坛公园 前门大街
D3 颐和园 圆明园
```

每条含：路线名称、天数、按天分组的推荐顺序、一句话说明。

**加到我的规划**不会直接塞坐标——方案里只有名字。逐个用腾讯搜索按名字重新定位，拿到坐标才加，
并按方案里的天落位、按顺序写 seq。同名地点跳过，搜不到的会列出来告诉你。

三种状态都有：加载中转圈、失败显示原因 + 重试、空结果显示提示 + 重试。

**诚实说明（界面底部也写了）**：这些方案是 DeepSeek 按其训练语料生成，**不是实时联网检索**。
冷门新景点它可能不知道。要真联网得另接搜索 API。

## 地点资料：高德补全 + AI 兜底

腾讯位置服务只给名称、地址、坐标、分类。营业时间、评分、人均、电话、图片这些它没有，
所以点「规划」时会做两步补全：

1. **高德 JS API**（`public/js/amap.js`）：按名称 + 城市搜 POI，取距离 3 公里内、名字最像的那条，
   拿 `rating / cost / opentime2 / tel / photos`。名字带括号门店后缀的会自动去掉再试一次。
2. **DeepSeek**（`ai.js` 的 `fillInfo`）：高德也没有的字段（小馆子的人均、冷门点位的营业时间）
   让模型估一个参考值，标 `AI`。

详情弹层只保留不重复的字段：上面是只读的**地址 / 地区 / 电话 / 坐标 / 评分**，
下面是能改的**分类 / 停留 / 营业时间 / 分到第几天 / 人均 / 门票 / 最晚到达**。
「分到第几天」和「分天」页签是同一个数据（`place.day`），在哪儿改都一样。
图片链接输入框去掉了——点位圆圈用的照片由高德自动带，不用手填。

**Key 的类型很关键**：手头这把是「Web端(JS API)」类型，配安全密钥才能在浏览器里用。
拿它去调 `restapi.amap.com` 会返回 `USERKEY_PLAT_NOMATCH`——那是「Web服务」平台才认的。
所以高德只用在这里补资料；搜索和路线规划仍走腾讯（跨域可用、已经调稳）。

补过的地点会打 `amapAt` 时间戳，**下次规划不会重复查**。

### 营业时间

腾讯位置服务不返回营业时间。点「规划」时会用 DeepSeek 补：只查**没填过**的地点，一次 10 个，
不确定的（海滩、街道、观景台）留空，**不编造**。补上的在详情里标 `AI`，可以手改；
改过之后 `hoursAi` 清掉，下次不会再查这个点。

## 导图格式：新版 XMind 只认 content.json

`.xmind` 是个 zip。很多人以为里面是 `content.xml`（XMind 8 时代的格式），
但**新版 XMind 写出的 content.xml 其实是一段警告占位**：

> 该文件无法正常打开，请勿修改并保存，否则文件内容将会永久性丢失！

真正的内容在 `content.json`。所以这里生成的是：

```
content.json    [{ id, class:'sheet', title, rootTopic: {...} }]
metadata.json   { dataStructureVersion, creator, layoutEngineVersion }
manifest.json   { 'file-entries': { 'content.json':{}, 'metadata.json':{} } }
```

zip 用纯 JS 打包（crc32 + 存储模式），不引第三方库，浏览器和 Node 同一份代码。

## 为什么导图不走浏览器下载

用浏览器下载 `.xmind`，Windows 会给文件打上「网络来源」标记（Mark of the Web），
双击打开时先弹一屏「这些文件可能对你的计算机有害」，XMind 直接被挡在系统层，
看起来像「XMind 报错」，其实文件是好的。

所以点「导图」时，前端把内容 POST 给本地服务，由 Node 直接写到 `travel-planner/exports/` 下。
本地生成的文件没有那个标记，XMind 打开不会有任何提示。

真遇到提示时的解法（老文件也一样）：点【确定】继续，或右键文件 → 属性 → 底部勾「解除锁定」→ 确定。

## 已知边界

- **跨天均衡会牺牲一点地理紧凑度**。当某天塞不下时，程序会把耗时最长的那个点挪到有空档的那天，
  由此可能产生一段 50–90 分钟的跨区移动（比如「故宫 → 颐和园」）。
  想避免就在卡片里手改「第X天」，或者把天数加够——手动指定优先级最高。
- **单段过长不会自动拆分**，也不会再弹提示；点开那段路看耗时，觉得不值就改天。
- **公交方案取第一条**，另存的备选方案只显示数量和耗时，不展示明细。
- **不做营业时间/闭馆日判断**：故宫周一是关的，工具不会拦你。要严格，用 `⏰` 自己设「最晚到达」。
- **不做住宿自动选址**：酒店、到达站、返程站都要你自己填名字，工具只负责解析坐标。
  名称必须是腾讯地图里存在的 POI，生造的酒店名会落到同名最近的一家，注意核对下方的 `✓` 提示。
- **区县来自接口的 `district` 字段**，只有「按地址添加」或没联网时，才退回从地址前缀里猜，
  猜不出来的归到「未分区」。
- **地址解析是模糊匹配**，匹配度低于 85% 时会提示你在图上核对落点，别直接信。
- **类别识别是规则表，不是模型**：连锁品牌覆盖得比较全，冷门店名可能落到「其他」，改一下分类即可。
- **评分、营业时间、人均消费没有**：腾讯位置服务不提供，工具不编。要这三项得换数据源。
- **天气只有未来 16 天**：行程日期太远会提示取不到预报，不影响规划。
- **不是真正的拖拽**：调顺序用时间轴上的 `↑ ↓`，换天用卡片里的「第X天」下拉。拖拽要重写整套时间轴渲染，这一版没做。
- **城际交通不排班次**：只排「到站之后」和「返程之前」，高铁/航班你自己订、自己填时间。
- **返程站跨城时不规划怎么去**：比如行程在厦门、返程站填了六安站，工具不会去算「酒店 → 六安站」——
  那样会排出一条 9 小时、换乘 4 次的假路线。这种情况直接标「返程（自行前往车站）」。
- **最后一天按发车时间倒推收工**：发车 14:00 → 13:30 到站；跨城返程再扣 30 分钟（住处到本地车站这段排不了，只能预留），
  即 13:00 必须玩完回酒店。排不下的景点会被裁掉，不会出现「19:27 还在景点、13:30 就说到站了」这种时间倒流。
- **儿童票按 6 折估算**：不区分景区免票线、儿童半价票的具体规则，改动请自行调住宿/餐饮单价。
- **营业时间冲突检测做不了**：没有营业时间数据，自然也无法判断"到得太晚已经关门"。
- **餐饮只是占位**：午餐按「就近用餐」插入 60 分钟，不做餐厅推荐。
- 地点超过 25 个、天数超过 14 天时，启发式规划质量会下降。
- 底图用的是高德栅格瓦片（无 Key 直连）。这是非官方接口，哪天失效了需要换源；
  换成 OSM 会导致标点整体偏移几百米（坐标系不同），别换。
- **本工具不校验首末班车**：深夜行程请自行核对卡片里显示的首班/末班时间。
